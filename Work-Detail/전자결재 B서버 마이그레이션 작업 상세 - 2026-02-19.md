**문제 분석**:
```bash
# Nginx 로그에 assets 요청이 기록되지 않음
sudo tail -f /var/log/nginx/access.log
# assets 요청이 나타나지 않음 → upstream으로 전달되지 않음

# Origin 헤더 포함하여 직접 테스트

# HTTP/1.1 403 Forbidden

# Spring Boot 로그 확인
docker logs app-green | grep CORS
# CORS policy: Request blocked due to invalid origin
```

**원인**: Spring Boot WebConfig.java에서 B서버 IP가 허용되지 않음

**해결 과정**:
```java
// src/main/java/com/kdcorpsign/config/WebConfig.java
@Override
public void addCorsMappings(CorsRegistry registry) {
    registry.addMapping("/**")
            .allowedOriginPatterns(
                "https://*.kdcorpsign.co.kr",
                "http://localhost:5173",
                "http://10.100.14.103:5173",    // 개발 서버 1
                "http://10.100.14.116:5173",    // 개발 서버 2
                "http://221.146.5.85"           // 🆕 B서버 IP 추가
            )
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .allowCredentials(true)
            .maxAge(3600);
}
```

// Jenkinsfile
pipeline {

## 🚨 트러블슈팅 케이스 분석

### Case 1: 네트워크 연결 실패

**문제**: A서버에서 B서버로 직접 scp 전송 시 100% 패킷 손실

**분석 과정**:
1. **Layer 3 (Network)**: `ping` 테스트 → 정상 응답
2. **Layer 4 (Transport)**: `telnet` 포트 테스트 → 연결 거부
3. **호스팅 업체 확인**: A서버 IP가 방화벽에서 차단됨

**해결책**: 전송 방향 역전 (B → A pull 방식)

**교훈**: 
- 서버 이전 시 네트워크 정책 사전 확인 필요
- 양방향 연결 테스트 중요성
- 호스팅 업체와의 사전 협의 필요

### Case 2: SELinux 보안 정책

**문제**: Nginx → Docker 컨테이너 연결 시 Permission denied

**분석**:
```bash
# SELinux 상태 확인
getenforce
# Enforcing

# 오류 로그 분석
sudo ausearch -m avc -ts recent
# type=AVC msg=audit: denied { name_connect } for comm="nginx" dest=3001
```

**해결**:
```bash
sudo setsebool -P httpd_can_network_connect 1
sudo semanage port -a -t http_port_t -p tcp 3001
```

**교훈**:
- SELinux 환경에서는 네트워크 연결 권한 별도 설정 필요
- 보안 정책과 애플리케이션 요구사항 간의 균형점 찾기

### Case 3: CORS 설정 불일치

**문제**: assets 파일 로드 시 403 Forbidden

**분석 단계**:
1. **Nginx 로그**: assets 요청 기록 없음
2. **직접 테스트**: Origin 헤더 포함 시 403 반환
3. **코드 분석**: WebConfig에서 B서버 IP 미허용

**해결**: 백엔드/프론트엔드 CORS 설정 동기화

**교훈**:
- 서버 IP 변경 시 CORS 설정 업데이트 필요
- 프론트엔드와 백엔드 설정의 일관성 유지
- 단계별 디버깅의 중요성

### Case 4: 빌드 도구 버전 호환성

**문제**: Vite 7.x와 Gradle 내장 Node.js 버전 불일치

**분석**:
- Gradle 내장: Node v20.11.0
- Vite 요구사항: Node v20.19+ 또는 v22.12+

**해결**: 빌드 프로세스 분리
- 프론트엔드: 시스템 Node.js 사용
- 백엔드: Gradle 사용

**교훈**:
- 개발/운영 환경 간 도구 버전 일치 중요성
- 의존성 관리의 복잡성 고려
- 빌드 프로세스 유연성 확보
