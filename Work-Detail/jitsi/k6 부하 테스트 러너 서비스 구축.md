# k6 부하 테스트 러너 서비스 구축

## 개요
관리자 대시보드에서 트래픽 부하 테스트를 실행할 때, 개발 PC나 브라우저가 아니라 **112번 서버의 독립 k6 러너**가 부하를 생성하도록 별도 서비스를 구축했다. 기존 백엔드는 권한·감사 로그만 처리한 뒤 러너의 내부 API를 호출하는 구조로, 부하 생성 책임을 전용 호스트로 분리하고 보안 경계를 명확히 했다.

## 관련 커밋
- `2026-07-20` `ad2c133` k6 수정 (러너 서비스 신설: `infrastructure/k6/runner/`)

> 백엔드 측 연동(`loadtest_service.py`, `admin_router.py`)은 [[K6 부하 테스트 및 서버 허용치 예측]] 참고.

## 주요 구현 내용
- **독립 job 러너** (`infrastructure/k6/runner/server.py`, 약 270줄): 표준 라이브러리(`http.server.ThreadingHTTPServer`)만으로 작성한 경량 러너. 허용된 시나리오(`traffic_summary`, `traffic_timeseries`)와 프리셋(`light`/`normal`/`heavy`)만 받아 k6 subprocess를 실행한다.
  - **단일 동시성**: `threading.Lock`으로 queued/running job이 하나라도 있으면 `LOADTEST_ALREADY_RUNNING`을 반환해 동시 실행을 차단.
  - **job 영속화·복구**: 각 job을 `/data/jobs/<job_id>/job.json`에 원자적 저장(`.tmp` → `replace`)하고, 러너 재시작 시 queued/running 상태로 남은 job은 `failed`로 정리한다.
  - **리포트 제공**: `GET /v1/jobs/{id}/report`로 HTML/JSON 리포트를 반환.
- **컨테이너 격리** (`runner/Dockerfile`, `runner-compose.yml`): `grafana/k6:0.58.0` 바이너리를 `python:3.12-slim`에 복사한 멀티스테이지 이미지. 비루트 사용자(uid 10001), `read_only` 파일시스템, `tmpfs`, `no-new-privileges`, `cap_drop: ALL`로 컨테이너를 하드닝했다.
- **보안 경계**: 기본 바인딩은 `127.0.0.1:8099` loopback. 외부 호스트 연결이 필요하면 사설/VPN 주소 + 방화벽 출발지 IP 제한이 전제이며, 공인 IP·공개 reverse proxy에는 노출 금지. 러너·백엔드 간에는 `K6_RUNNER_TOKEN` 공유 비밀값(Bearer)으로 인증한다.
- **환경 고정**: `TARGET_BASE_URL`(기본 스테이징), `K6_TEST_USER_ID`(`MONITORING_READ`만 가진 테스트 전용 계정)를 `runner.env`의 고정값으로만 사용해 하드코딩과 실계정 사용을 배제했다.
- **Prometheus 연동**: k6 결과를 remote write로 관제 Prometheus에 보내 Grafana `Traffic Monitoring` 대시보드에서 부하 곡선과 서버 지표를 같은 시간대에 겹쳐볼 수 있게 했다.

## 데이터 흐름
```
관리자 브라우저 → 기존 백엔드 /api/meeting-admin/loadtest/**
                       │ (K6_RUNNER_TOKEN 공유 비밀값)
                       ▼
                112번 k6 러너 ──► TARGET_BASE_URL 관리자 API
```

## 비고
회의 참가·미디어(XMPP/WebRTC) 부하는 이 러너 대상이 아니며 `jitsi-meet-torture` 등 별도 도구로 검증한다. 러너는 관리자 트래픽 API(`/api/meeting-admin/traffic/*`)만 부하 대상으로 삼는다.
