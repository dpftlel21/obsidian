### 📝 문제 설명
> [!bug] **What happened?**
> 
> **현상**: 
> - `URL.createObjectURL(blob)`을 사용하여 생성된 URL은 브라우저의 document가 unload될 때까지 메모리에 해제되지 않고 남아있음.
> - 안전보건 관리 팝업처럼 이미지를 자주 열고 닫거나, 많은 이미지를 조회하는 경우 가비지 컬렉션(GC)이 되지 않아 메모리 사용량이 지속적으로 증가할 수 있음.
> 
> **발생 시점**: 
> - 수리·보수 전/후 이미지 조회 팝업을 반복적으로 열고 닫을 때
> - 이미지가 포함된 데이터를 계속해서 새로 불러올 때
> 
> **영향 범위**:
> - 안전보건 관리 팝업 (SafetyHealthPopMaintenance)
> - Blob 이미지를 사용하는 모든 컴포넌트

### 🔍 환경 정보
| 항목 | 정보 |
|------|------|
| **OS/플랫폼** | Windows, macOS |
| **브라우저** | Chrome, Edge, Safari (모든 브라우저 공통) |
| **관련 API** | URL.createObjectURL, URL.revokeObjectURL |
| **데이터 유형** | Blob (Binary Large Object) |

## 🔬 근본 원인 분석 (Root Cause Analysis)

### 📊 5 Whys 분석
1. **Why 1**: 왜 메모리 누수 위험이 있는가?
   - 답: `createObjectURL`로 생성된 URL 객체는 브라우저 내부 매핑 테이블에 저장되며, JS 가비지 컬렉터가 자동으로 정리하지 않기 때문.

2. **Why 2**: 왜 자동으로 정리되지 않는가?
   - 답: 브라우저 사양상 해당 URL이 언제 더 이상 필요 없는지(참조가 끝났는지) 브라우저가 명확히 알 수 없으므로, 개발자가 수동으로 해제하기 전까지 유지하도록 설계됨.

3. **Why 3**: 이전에는 왜 문제가 되지 않았나?
   - 답: 이전에는 이미지 URL 스트링을 직접 사용했거나, Blob 처리를 하지 않았기 때문일 수 있음. 이번 작업에서 Blob 데이터를 직접 다루면서 이슈가 부상함.

### 🎯 근본 원인
> [!important] **Root Cause**
> 
> **주원인**: Blob 객체의 라이프사이클 관리 부재
> 
> **상세**: 브라우저 메모리 힙(Heap)에 Blob 데이터에 대한 참조가 계속 쌓이는 구조적 특성. 명시적인 `revoke` 호출 없이는 세션 종료 시까지 메모리를 점유함.

## 💡 해결 방안 (Solutions)

### 🔧 적용된 해결책 (Permanent Solution)
> [!success] **Implemented Fix**
> **방법**: React `useEffect`의 cleanup 함수를 활용한 자동 해제 구현
> 
> **구현 코드**:
> ```typescript
> useEffect(() => {
>     if (beforeImageBlob) {
>         // 1. URL 생성
>         const url = URL.createObjectURL(beforeImageBlob)
>         setBeforeImageUrl(url)
>         
>         // 2. Cleanup 함수 반환: 컴포넌트 언마운트 또는 blob 변경 시 실행
>         return () => {
>             URL.revokeObjectURL(url) // 메모리 해제
>         }
>     }
> }, [beforeImageBlob])
> ```
> 
> **원리**: 
> - 컴포넌트가 사라지거나(팝업 닫기), 새로운 이미지가 로드되기 직전에 `revokeObjectURL`을 호출하여 브라우저에게 "이 URL은 더 이상 쓰지 않는다"고 통보.
> - 브라우저는 해당 Blob 매핑을 제거하고 메모리를 확보.

### 📝 교훈 및 인사이트
> [!learn] **Lessons Learned**
> 
> 1. **브라우저 리소스 관리**: React의 가상 DOM 외부(브라우저 API 등)에서 생성된 리소스는 반드시 수동으로 정리(Clean-up)해야 함을 재확인.
> 2. **useEffect의 중요성**: `useEffect`의 return 함수가 리소스 정리의 핵심 장소임을 활용.
> 3. **Blob vs Base64**: Base64는 문자열이라 GC가 자동 관리해주지만 용량이 33% 커짐. Blob은 효율적이지만 수동 관리가 필요함. 대용량 이미지 처리에는 Blob이 적합하므로 이 패턴을 유지하는 것이 좋음.
